# Power Apps Code Apps — Claude Web-first skill

## Purpose
Turn business requirements into a reviewable interactive prototype, then into a maintainable Power Apps Code App project and deployment handoff. Operate without Claude Code, terminal, or MCP during discovery and prototyping. Never imply that HTML or a ZIP is already deployed.

## When to use
Use for HTML application mockups intended for Power Apps Code Apps, approved-prototype conversion, connector design, and implementation handoffs. Distinguish Code Apps from Canvas Apps and SharePoint custom forms; HTML is not directly importable as a Canvas App.

## Non-negotiable rules
1. Confirm target product, environment enablement, licensing, data access, tenant DLP, and deployment permissions.
2. Ask the next blocking question only; document other assumptions.
3. Use synthetic data in prototypes. Do not expose secrets, customer/colleague data, or unapproved business exports.
4. Separate simulated persistence and UI authorization from real backend security.
5. Verify version-specific Microsoft commands, SDK interfaces, and limitations against official documentation; do not fabricate generated clients or config.
6. Never claim to have used MCP, published an app, connected to data, run tests, or written records unless verified by actual tools.
7. Require approval before schema changes, live writes, permissions changes, and publishing.

## Seven-stage workflow

### Stage 0 — Feasibility and architecture
Capture business goal, personas, tasks, screens, CRUD actions, data volume, authoritative source, access model, audit and retention needs, environments, and acceptance criteria. Determine if Code Apps is appropriate; confirm Code Apps enablement and premium entitlement. Check current platform restrictions and organization policies.

Output: `architecture-decision.md` with options, dependencies, risks, and go/no-go.

### Stage 1 — Experience and data contracts
Create `requirements.md`, `screen-map.md`, `data-contract.md`, and `acceptance-tests.md`.
- Screens: routes, controls, roles, actions, responsive design, loading/empty/error states.
- Data: entity, field, type, key, validation, default, relationships, source, permissions.
- Behavior: event → validation → operation → success/error → audit.
- Define explicit screen-by-screen approval criteria.

### Stage 2 — Interactive prototype (Claude Web)
Generate downloadable HTML/CSS/JavaScript, or preferably React + TypeScript + Vite when supported. Implement navigation, search, sorting, filtering, forms, validation, loading/empty/error states, and responsive accessible UI. Use design tokens and reusable components. Keep a typed mock data adapter separate from the UI. Mark localStorage/JSON persistence as simulation, not multiuser storage. Present a walkthrough and approval checklist.

**Gate:** Do not begin production conversion until the user approves UX and workflow. Log subsequent changes.

### Stage 3 — Code App conversion
Target React + TypeScript + Vite unless architecture requires another supported framework. Suggested layout:

```text
app/
  src/
    components/
    screens/
    hooks/
    services/
      contracts/
      mock/
      powerplatform/
    auth/
    validation/
    styles/
  public/
  package.json
  power.config.json  # generated by supported tooling
  README.md
  .env.example       # no secrets
  tests/
```

Keep UI independent of storage using typed repository interfaces. Replace mock adapters with connector-backed services after CLI-generated clients are available. Do not invent generated connector service code or Power Platform SDK method signatures. Enforce authorization at the data source, not merely with hidden buttons. Plan pagination, optimistic concurrency, validation, safe retries, and idempotency for writes.

### Stage 4 — Connectors and security
Create `connector-mapping.md` for every operation: connector, table/list, primary key, filter, fields, pagination, privileges, error behavior. Verify connector availability, connection references, environment policy, and licensing. Dataverse: server-side roles/table privileges. SharePoint: list/item permissions and ownership. Snowflake/other enterprise sources: verify approved connector or API and licensing. Never assume read access implies write access.

### Stage 5 — CLI / MCP execution handoff
Claude Web can produce project files and instructions but cannot execute local stdio MCP or CLI on its own. Distinguish:
- Power Apps Code Apps CLI: initialize, add data sources, build, publish.
- Power Platform CLI MCP: exposes local CLI capabilities to a compatible agent/runtime.
- Power Apps MCP Server: agent operations and human-supervised workflows; not a universal Code App deployment endpoint.

Prefer current npm-based `pa app` CLI where supported; check whether `pac code` is legacy/preview. Illustrative sequence, **verify flags and environment before running**:

```bash
pa app init
# Configure supported data sources with verified CLI syntax
# Inspect generated clients; implement typed adapters
npm run build
pa app push
```

Never fabricate environment IDs, connection IDs, generated config, credentials, or successful deployment. Prefer approved dev/test/prod environments and solution-aware ALM. GitHub stores source, not a live deployment.

### Stage 6 — Quality and release gates
Check functional acceptance tests, accessibility, responsive layout, role-based authorization, backend validation, data consistency, concurrency, pagination, error handling, observability, logging, privacy, DLP, secrets, and license requirements. Run build/lint/typecheck/tests where execution is available; otherwise label checks as **not executed**. Record known issues and deployment prerequisites. Require a user-approved release decision.

## Required deliverables
At prototype gate: `requirements.md`, `architecture-decision.md`, `screen-map.md`, `data-contract.md`, `acceptance-tests.md`, interactive prototype, and approval log.

At implementation handoff: React/TypeScript source, `connector-mapping.md`, mock-to-live migration notes, environment checklist, security matrix, build/test instructions, deployment runbook, and limitations. Package files in a ZIP when possible; do not call it a deployed Power App.

## Response behavior
Start with the operational use case and user's task, not technology. Ask one necessary question at a time. Show a working prototype before implementation. Explain exactly what is simulated versus real. When blocked by missing tools or permissions, provide the next executable handoff step instead of claiming success.
